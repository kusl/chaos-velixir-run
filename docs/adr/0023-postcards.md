# 0023 Postcards: one long message with images

Status: accepted

- `/postcard` hosts `PostcardIsland`. The server keeps one postcard, the newest; each accepted one replaces it. No jackpots, no winners.
- Limits (`PostcardRules`, mirrored in `PostcardIsland.razor.js`): 5,000 characters (`MessageText` with a longer limit), up to 4 images, PNG, JPEG or GIF, 2 MB each, 4 MB together, at most 4,096 px a side and 4,096² px, GIFs at most 1,000 frames. Text or at least one image is required. A postcard identical to the current one (text and image bytes) is refused.
- Why these numbers: one postcard is at most 4 MB in memory, plus at most `PostcardUploads` (default 2) uploads in flight, well inside 256 MB; 5,000 characters stay under the 32 KB hub message limit even as 3-byte UTF-8.
- Rate: `PostcardBurst` 2, `PostcardsPerSecond` 0.1 per client. Size and count are checked before the rate bucket and before any upload. When every upload slot is taken, image postcards get `busy`.
- Upload: the module handles submit itself and calls `Send(text, images, meta)`. Images go as `DotNet.createJSStreamReference(blob)` and are read with `OpenReadStreamAsync`, chunked under the hub limit. No HTTP upload endpoint, so origin checks and limits stay on the circuit.
- The browser drops control characters and lone surrogates before sending. JPEG and PNG over 2 MB or 4,096 px are redrawn on a canvas to 2,048 px JPEG at 0.85, which also applies EXIF rotation. GIFs are sent as they are or refused.
- `ImageSanitizer` decides the type from the bytes, never the name or MIME type, walks the file structure, and rebuilds it: PNG keeps rendering chunks only (no `tEXt`, `zTXt`, `iTXt`, `eXIf`, `tIME`) and refuses unknown critical chunks; JPEG drops `APP1`–`APP15` except ICC and Adobe, and `COM`, then writes a 34-byte EXIF with only the orientation when it was not 1; GIF drops comments, plain text and application extensions other than looping. Anything truncated, unknown or out of range is refused.
- Wire: `PostcardUpdate { kind, version, card }`, `kind` `snapshot` on join and `change` after. A card is `{ id, text, images: [{ type, width, height, length }], meta? }`. Bytes never travel over the circuit to viewers.
- Images: `GET /postcard/images/{id}/{index}` serves the current postcard only, `private, max-age=31536000, immutable`, 404 otherwise. The prerender uses these URLs; the module fetches each image once, checks its length and stores it.
- Local history: database `chaos-postcards` v1, stores `cards` (`{ id, text, images, meta?, mine? }`), `images` (`{ key: "<id>/<index>", id, blob }`) and `state` (`bytes`). 10,000 cards; images up to 256 MB, oldest images evicted first while their text stays. On a quota error the card is saved without images. Missing images show `Image n of m was not kept`. Images are shown from `blob:` URLs, so the CSP allows `img-src 'self' blob:`; URLs are revoked when the feed is redrawn or the island is disposed.
- Feed: the live postcard plus 20 stored ones, a button for 20 more. Every postcard but the live one has a dotted border.
- After a restart (snapshot without a card) the browser offers its newest postcard once per circuit, images included, if all of them are stored. `WouldRestore` checks the UUIDv7 before any upload; the server accepts it only if it is older than the server start and newer than the current postcard, with normalized text and details and clean images.
- Details and `Your message` work as on the board (ADR 0022) and share the `chaos-board-share` setting. The browser marks its own postcards `mine` from the `Send` reply.
